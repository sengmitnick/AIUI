让 UI 在眼镜里
退一步。

单绿低干扰空间 HUD 不是另一套皮肤，而是一套空间决策。 眼镜是看世界的窗口；480 × 352 只是坐标与安全边界，不是需要填满的手机屏幕。 默认把常驻信息放在下方，将中央留给现实与真正的任务内容。

WINDOW, NOT SCREEN BOTTOM BY DEFAULT ONE ATTENTION PEAK TRANSPARENT BY DEFAULT

01 / CORE PRINCIPLE

把“全屏 Page”与“全视野 UI”分开。

全屏 Page 是运行时的承载方式，不是视觉形态。透明眼镜中，通用标题、菜单、状态栏和按钮不应因为有整块画布就占据整块画布。 每一束亮光都要有任务理由。

01 / QUIET

无事发生时，什么也不显示。

等待、聆听、后台同步等静默状态不需要常驻装饰。留白本身就是对现实世界的尊重。

02 / LOWER FIELD

常驻信息默认停在下方。

短提示、状态与一个动作形成稳定的低位锚点，不挤占中心任务内容和上方视野。

03 / TASK CONTENT

中央只属于任务本身。

阅读内容、配对码、角色、游戏或相机画面可以进入中央；通用应用 chrome 不可以。

i
“下方优先”来自产品迭代与佩戴体验的默认偏好，不是所有用户、所有眼镜的生理定律。它必须经由真机、不同背景和真实任务校准。

02 / PLACEMENT GRAMMAR

先选位置，再选组件。

一个稳定页面状态先选择一种空间模式。不要把“更多信息”理解成“更多区域都该亮起来”。 当任务变化，模式才变化；完成后，优先回到更安静的状态。

04 / ATTENTION BUDGET

不是组件数量，而是注意力总量。

单绿系统已经规定亮度 token；空间 HUD 进一步限制每个稳定状态可以同时要求用户注意多少东西。 一眼能说出“现在看什么”，才是有效的层级。

常规状态的预算

  • bright value · 1最亮的文字、数字或动作只留给当前必须注意的事。
  • strong outline · 1强描边只标识当前焦点、活动目标或被检查的任务内容。
  • local fill · 0–1填充只支撑局部选择，最高为 primary-12。
  • persistent copy · 2一个下方主栏加一个页脚；其余信息合并、按需出现或顺序呈现。

焦点如何切换

  • inactive · open未选菜单项是文字、图标或安静分隔线，不是同亮度的卡片。
  • focused · framed当前项获得唯一的强框、方向标记与可选的局部浅填充。
  • stable footprint焦点变化不改变列表几何尺寸，不让周边元素闪烁或跳动。
  • resolve · quiet确认、超时或完成后，选择器消失或降级为简短结果。
Anti-pattern 01

大面积绿色或黑色背景

它把真实世界当成要被遮掉的内容。先删背景，再删容器，最后才判断是否需要局部线框。

Anti-pattern 02

每个选项一个同样亮的框

这会强迫用户横向扫视并让所有选择同时竞争。强焦点应该是稀缺资源。

Anti-pattern 03

把完成后的 UI 留在屏幕上

一个已完成的配对、同步或确认不应继续发光。结果无须比过程更喧闹。

05 / ITERATION EVIDENCE

从四个应用的迭代中提炼，而不是复制某一张截图。

这些模式来自同一条产品演进：先识别手机式、卡片式和仪表盘式的视觉负担，再把常驻 chrome 收束到边缘，让内容本体得到它真正需要的空间。

别卡壳 / LOWER RAIL

去掉上方状态与中央大框。

词条、配对和操作提示收进下方主栏；计时与手势提示沉到页脚；时效只用一条细线表达。

剧本杀助手 / SINGLE FOCUS

去除共享 HUD 色块。

同一交互分组只保留一个完整焦点框。未选项是安静的空间与文字，而不是一墙等权的发光控件。

赛博宠物 / CENTER AS CONTENT

角色可以在中央，但 chrome 不可以。

宠物是语义内容，所以可以拥有中心；雷达、扫描环、仪表和冗余外壳被移除，状态与控制仍然下沉。

尖叫酷跑 / IMMERSIVE EXCEPTION

全屏内容不等于全屏界面。

游戏世界可占画布，因为它就是任务；得分、音量、提示等通用 chrome 仍然退到边缘或地面。

06 / AIUI RUNTIME RECIPE

AI 要加载同一份规则；运行时只用已确认能力。

本 profile 直接镜像到现有 aiui-dev Skill 的按需 reference 中。 对符合条件的单绿全屏 Page：先加载基础 monochrome-green，再加载空间 HUD 规则；不会新建独立 Skill，也不会把规则误套给对话卡片或普通 Widget。

非导航性 HUD 分组优先使用透明的 <view>；只有导航语义成立时才使用 <card>。
用已支持的 position: relative / absolute 和 transition 表达锚点与状态变化；不要将浏览器 CSS 动画、keyframes 或 sticky 当成可依赖能力。
完成后的收束应由数据状态驱动：移除覆盖层或切换到更安静状态，而不是保留一段装饰动画。

07 / ON-DEVICE REVIEW

一张黑底截图通过，不代表眼镜上通过。

浏览器中的黑色只是在模拟透明显示。每个稳定状态都要放回真实背景里，检查用户正在走路、转头、看远处时，HUD 是否仍然克制且可用。

BACKGROUND

暗、亮、杂乱

关键文字与图标是否仍在安全区内可读？语义是否仍然不只依赖绿色亮度？

MOTION

静止、行走、转头

顶部、中央或全画布内容是否有足够任务理由？是否会压过现实环境的注意力？

FOCUS & EXIT

确认、返回、完成

焦点是否唯一且稳定？确认或超时之后，界面会不会立刻消失或安静下来？

✓
最终问题很简单：如果删掉这块 HUD，用户会不会失去当前任务所需的信息？如果不会，优先让它消失。
